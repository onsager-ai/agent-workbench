# Visuals for complicated decisions

The question tool already shows the options and their trade-offs, so don't draw them again in a visual. Show a visual only when the problem itself is complicated, such as a multi-step mechanism or a comparison of states that would take more than a few paragraphs to explain. Then show one compact visual of the problem before asking: the scenario as numbered steps or a simple flow, grounded in the actual code, configuration or data. Most decisions need no visual.

The user often reads on a phone, so design the visual for a 360 px wide screen first. Lay it out in one column, with nothing side by side and nothing that scrolls sideways. Use plain words rather than internal jargon, readable text (at least 15 px) and clear contrast. A table is fine only with two or three narrow columns. For an SVG, set the `viewBox` about 360 wide; a 700-wide `viewBox` shown at phone width halves every font size. Keep the visual to about one phone screen; if it doesn't fit, cut words rather than shrinking text. Use the harness's inline render tool where available (for example, T3 Code `html_render`); otherwise use a small diagram or table in the message.
