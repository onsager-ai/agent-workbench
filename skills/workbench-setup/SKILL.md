---
name: workbench-setup
description: Install, inspect, update, or remove Agent Workbench shared global instructions and its local launcher while preserving personal instruction text.
---

Use the bundled Node.js 22.20+ installer on Linux or macOS. Native `npx skills` distributes this skill; it does not execute the installer or apply global prompts.

`workbench.mjs help <command>` and `<command> --help` show command usage. `status` prints a readable checklist; use `status --json` for the same machine-readable status fields.

Orchestration's interactive Manager, native Worker ladder and configured context policy live in the `orchestrate-harnesses` skill. Window values come from base `policy.context` in the Worker configuration, not skill or role instructions. Updating that skill changes its distributed defaults, not the current Manager's interactive model/settings or the user's partial model overrides.

After global distribution, explicitly apply the setup:

```sh
node ~/.agents/skills/workbench-setup/scripts/workbench.mjs install
awb status  # alias for the installed agent-workbench command
awb trust  # optional: consent to trust installed Codex hooks
# Or use ~/.local/bin/agent-workbench status and trust
```

The installer creates `~/.agents/AGENTS.md`, links Codex's `~/.codex/AGENTS.md`, and ensures `~/.claude/CLAUDE.md` has one native import resolving to the shared instructions. An existing equivalent Claude import is reused. Personal text belongs outside `<!-- BEGIN agent-workbench -->` / `<!-- END agent-workbench -->` and the optional `<!-- BEGIN agent-workbench personal -->` / `<!-- END agent-workbench personal -->` block in the shared file. When `~/.agents/skills/workbench-personal/AGENTS.md` exists, install applies it in that second block immediately after the public block; removing the package or file removes the owned personal block on install. Both blocks have ownership and drift checks; edit the package source instead of the installed personal block. Existing Codex regular-file bytes are kept outside the managed block on first installation; existing Claude text stays in its file.

`agent-workbench install` reapplies distributed assets. On Linux with a supported sensor and user systemd, opt in to the thermal logger with `awb ops thermal install` or `agent-workbench ops thermal install`. Use the corresponding `ops thermal uninstall` command before removing the skill if you enabled the logger. `agent-workbench update` first updates installed skills owned by `onsager-ai/agent-workbench` plus `workbench-personal` from any source through the native skills lock, then runs freshly distributed setup code. Node.js 22.20+ is the only runtime needed (`npx` distributes and updates the skills). Do not edit the native skills lock yourself.

When `orchestrate-harnesses` is installed, `install` (and `update`) generates one Claude Code subagent per routable tier at `~/.claude/agents/<tier>.md`. Distributed `workers.yml`, optional `~/.agents/skills/workbench-personal/workers.yml`, the partial user override (in that precedence order), and every profile contribute to this union. A tier is routable when it has `harness: claude` (using `model`) or a non-null `claude_route`. The default ladder maps L1, L2 and L3 to haiku, sonnet and opus. The optional `codex` profile maps luna and haiku to L1, sol and sonnet to L2, and adds opt-in terra with null routes, so Claude Managers run Codex Workers as `codex exec` unless a user override supplies a gateway model ID. Users can map any models to levels in `workers.yml`. Change a route in the YAML override, or set it to null to remove it when no profile needs it. A tier name must use the same model, route and effort across profiles; rename conflicting tiers. Each agent carries model and effort in frontmatter and the Worker instructions as its prompt. When renaming tiers, update the tier keys, ladder entries, and dispatch references together. Rerun `agent-workbench install` after edits and start a new session. Without `orchestrate-harnesses` no agents are generated.

For custom gateway aliases and a copyable CC Switch example, see [neutral Worker profiles](references/worker-profiles.md).

Use `agent-workbench workers --cwd PATH` to print effective JSON and the selected profile. Overrides live at `$XDG_CONFIG_HOME/agent-workbench/workers.yml` when XDG is nonempty and absolute, otherwise `~/.config/agent-workbench/workers.yml`. Unknown keys and invalid configuration fail installation without changing managed files. The `yaml` and `smol-toml` packages are vendored; installation never runs `npm install`. Setup owns a resolved `workers.json` beside `state.json` and passes its path to the policy hook. The hook selects approval rules by dispatch cwd; missing or unreadable policy asks for approval and requests reinstall. Uninstall removes the unmodified owned JSON along with the agents and hook entries.

Generated agent files are recorded with content hashes in the state file. Setup never overwrites a file it does not own, or an owned file you edited, and reports a conflict instead; other files in `~/.claude/agents` are left alone. `status` lists owned agents, personal package presence and applied personal files; `uninstall` removes unmodified owned agents.

When `orchestrate-harnesses` is installed, setup adds four Claude Code `hooks.PreToolUse` entries, one `hooks.PostToolUse` entry matching `Agent|Task`, and one `hooks.Stop` entry in `~/.claude/settings.json`, all running the installed `orchestrate-harnesses/scripts/policy-hook`. The PreToolUse entries match `Agent|Task`, `Bash`, and `mcp__t3-code__delegate_task` to require approval for L3 Workers (Opus by default), deny GitHub polling commands, and require explicit Worker models for built-in agents and T3 delegation. The hook always prompts for `model: opus` and denies `model` overrides on named agent types. PostToolUse checks the resolved route at async launch and checks the route and transcript models on completed runs. It reports the observed model if the configured model is an alias and the hook lacks its effective target. The Stop entry blocks turns that end in a prose question, directing the model to re-ask through AskUserQuestion. State records the exact entries setup added; foreign entries (including identical pre-existing ones) remain unowned. Status lists owned hooks as applied or missing; install re-adds a missing or edited owned entry and leaves the edited copy as yours, a duplicated owned entry causes a conflict, and uninstall removes only owned entries while preserving other settings and their key order.

Optional `policy.stop_classifier` defaults to null. Set `{url, model}` to classify the Stop hook’s prose-question check. This sends each turn’s final assistant message to that URL, so use the local Magpie gateway. A confident yes blocks, a confident no passes, and uncertainty or request failure falls back to the question-mark check.

When `~/.codex` also exists, setup writes the same policy to `~/.codex/hooks.json` (Codex 0.141 or newer, where hooks are on by default): PreToolUse groups for `Agent|spawn_agent`, `Bash`, `mcp__t3_code__delegate_task` and `mcp__t3_code__t3_thread_send`, plus a `Stop` group, each running `policy-hook --host codex`. Ownership follows the Claude rules above. Codex cannot prompt from a hook, so every approval the Claude hook would ask for (L3 or approval-required tiers) becomes a deny that tells the model to get your approval and retry, and the rule against inheriting the Manager's model does not apply. Codex runs a user hook only after it is trusted. Install writes the hook entries without trusting them. Run `agent-workbench trust` to review and consent to adding owned `[hooks.state."<key>"]` tables with `trusted_hash` to `~/.codex/config.toml`; without a terminal, or when you decline, it prints the `/hooks` step to trust them in Codex. A foreign `hooks.state` entry for the same key is left alone and reported. Status adds `codex_hooks` (applied or missing) and `codex_trust` (trusted, untrusted, or modified), with JSON output available through `status --json`. Uninstall removes only the owned tables that are still unmodified. Editing an owned hook's command or timeout, or moving it in `hooks.json`, changes its hash or key, so it becomes untrusted until install runs again.

`agent-workbench uninstall` removes both managed instruction blocks and owned import/launcher, and makes Codex's file regular again with the current private text. Backups remain private under `~/.local/state/agent-workbench/backups`; uninstall never restores stale snapshots over later edits. This is the normal rollback operation. Review retained backups manually for historical recovery.

If a command reports an override, foreign entry, missing resource, or edited managed block, preserve the files and resolve that specific conflict before retrying. There is no force-overwrite mode. State and lock live under `~/.local/state/agent-workbench/`.

Base `policy.context` applies across directories. `manager_window` is a positive integer (default `200000`); set it to `null` to disable the per-model override. `manager_models` defaults to `[claude-opus-5-5]`. Use the canonical ID for built-in models and the exact ID for gateway aliases. Claude Code supports configured windows of at least 100,000 tokens.

When the Claude Code config directory exists, installation manages `autoCompactWindow` from `max_tokens`, `modelSettings.<model>.autoCompactWindow` from `manager_window` for each `manager_models` entry, and optional `env.CLAUDE_CODE_MAX_CONTEXT_TOKENS` from `gateway_window` for unknown gateway IDs without `[1m]`. With neither `gateway_window` nor an absolute compaction window, Claude Code assumes 200k for those IDs, and routed Codex Workers can compact early, thrash autocompact, and stop using tools. Per-model compaction requires Claude Code v2.1.288 or later. Install removes the previous owned `env.CLAUDE_CODE_AUTO_COMPACT_WINDOW` when its value still matches state. A user-set copy takes precedence over both window settings. Install and status warn when a Worker tier shares a Manager model and its window.

When the Codex config directory exists, installation manages `model_auto_compact_token_limit` and optional `model_context_window`. Set `-c model_auto_compact_token_limit=<manager_window>` in the launch arguments for a Codex Manager only, for example in T3 Code's Codex provider launch arguments. `codex exec` Workers use the shared limit.

Setup preserves other settings, including provider routing and existing compaction windows that already match. A differing foreign value or an edited owned value conflicts. Missing managed values are reapplied. Status reports each key and uninstall removes only unmodified owned values. Restart running sessions to pick up changes. At the cap the harness compacts in place in the same thread and the Manager takes no action. Compaction does not enforce a hard request-token limit. Setup leaves project files, shell configuration, credentials, and permissions alone. Setup leaves unrelated skills alone and removes an owned `manage-lane` copy once its replacement is installed from the same ref.

For isolated fixtures, put the skill at the canonical location under a disposable home, then pass `--home PATH` before the command. Alternate-home updates require an explicit `--skills-cmd` executable command; they never default to the real user's npx update. Native permission choices remain with the user.
