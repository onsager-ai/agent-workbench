---
name: workbench-setup
description: Install, inspect, update, or remove Agent Workbench shared global instructions and its local launcher while preserving personal instruction text.
---

Use the bundled Node.js 22.20+ installer on Linux or macOS. Native `npx skills` distributes this skill; it does not execute the installer or apply global prompts.

`workbench.mjs help <command>` and `<command> --help` show command usage. `status` prints a readable checklist; use `status --json` for the same machine-readable status fields.

Orchestration's interactive Manager, native Worker ladder and configured context policy live in the `orchestrate-harnesses` skill. Window values come from base `policy.context` in the Worker configuration, not skill or role instructions. Updating that skill changes its distributed defaults, not the current Manager's interactive model/settings or the user's partial model overrides.

After global distribution, explicitly apply the setup:

```sh
node ~/.agents/skills/workbench-setup/scripts/workbench.mjs install
awb status  # alias for the installed agent-workbench command
awb lanes   # open PRs and local worktrees
awb trust  # optional: consent to trust installed Codex hooks
# Or use ~/.local/bin/agent-workbench status and trust
```

The installer creates `~/.agents/AGENTS.md`, links Codex's `~/.codex/AGENTS.md`, and ensures `~/.claude/CLAUDE.md` has one native import resolving to the shared instructions. An existing equivalent Claude import is reused. Personal text belongs outside `<!-- BEGIN agent-workbench -->` / `<!-- END agent-workbench -->` and the optional `<!-- BEGIN agent-workbench personal -->` / `<!-- END agent-workbench personal -->` block in the shared file. When `~/.agents/skills/workbench-personal/AGENTS.md` exists, install applies it in that second block immediately after the public block; removing the package or file removes the owned personal block on install. Both blocks have ownership and drift checks; edit the package source instead of the installed personal block. Existing Codex regular-file bytes are kept outside the managed block on first installation; existing Claude text stays in its file.

The Antigravity target is opt-in: run `agent-workbench install --antigravity` (or `node ~/.agents/skills/workbench-setup/scripts/workbench.mjs install --antigravity`) to add `@[Work instructions](~/.agents/AGENTS.md)` to `~/.gemini/AGENTS.md` and link installed Workbench skills into `~/.gemini/config/skills`. The native skills lock selects packages sourced from `onsager-ai/agent-workbench` plus the reserved `workbench-personal` entry, regardless of its source; unrelated packages are not exposed. Setup owns only links it creates, leaves existing correct links in place as user-owned, and removes its own links on uninstall. It does not install hooks. Existing instruction file content is preserved, and uninstall removes only the include line recorded as owned by Agent Workbench; an identical line that was already present remains user-owned. See the workbench-setup skill for the full setup workflow.

`agent-workbench install` reapplies distributed assets. On Linux with a supported sensor and user systemd, opt in to the thermal logger with `awb ops thermal install` or `agent-workbench ops thermal install`. Use the corresponding `ops thermal uninstall` command before removing the skill if you enabled the logger. `agent-workbench update` first updates installed skills owned by `onsager-ai/agent-workbench` plus `workbench-personal` from any source through the native skills lock, then runs freshly distributed setup code. Node.js 22.20+ is the only runtime needed (`npx` distributes and updates the skills). Do not edit the native skills lock yourself.

When `orchestrate-harnesses` is installed, `install` (and `update`) generates one Claude Code subagent per routable tier at `~/.claude/agents/<tier>.md`. Distributed `workers.yml`, optional `~/.agents/skills/workbench-personal/workers.yml`, the partial user override (in that precedence order), and every profile contribute to this union. A tier is routable when it has `harness: claude` (using `model`) or a non-null `claude_route`. The default ladder maps L1, L2 and L3 to haiku, sonnet and opus. The optional `codex` profile maps luna and haiku to L1, sol and sonnet to L2, and adds opt-in terra with null routes, so Claude Managers run Codex Workers as `codex exec` unless a user override supplies a gateway model ID. Users can map any models to levels in `workers.yml`. Change a route in the YAML override, or set it to null to remove it when no profile needs it. A tier name must use the same model, route and effort across profiles; rename conflicting tiers. Each agent carries model and effort in frontmatter and the Worker instructions as its prompt. Rerun `agent-workbench install` after edits. Without `orchestrate-harnesses` no agents are generated.

Use `agent-workbench workers --cwd PATH` to print effective JSON and the selected profile. Overrides live at `$XDG_CONFIG_HOME/agent-workbench/workers.yml` when XDG is nonempty and absolute, otherwise `~/.config/agent-workbench/workers.yml`. The `yaml` and `smol-toml` packages are vendored; installation never runs `npm install`. Setup owns a resolved `workers.json` beside `state.json` and passes its path to the policy hook. The hook selects approval rules by dispatch cwd; missing or unreadable policy asks for approval and requests reinstall. Uninstall removes the unmodified owned JSON along with the agents and hook entries.

Generated agent files are recorded with content hashes in the state file. Setup never overwrites a file it does not own, or an owned file you edited, and reports a conflict instead; other files in `~/.claude/agents` are left alone. `status` lists owned agents, personal package presence and applied personal files; `uninstall` removes unmodified owned agents.

When `orchestrate-harnesses` is installed, setup adds Claude Code `hooks.PreToolUse`, `hooks.UserPromptSubmit`, `hooks.PostToolUse` and `hooks.Stop` entries in `~/.claude/settings.json`, all running the installed `orchestrate-harnesses/scripts/policy-hook`. PreToolUse matches all tools; PostToolUse matches `Agent|Task` to validate Worker routes. The hook also denies GitHub polling commands, applies Manager work-call gates, and enforces observable Worker restrictions for thread creation, new watches and local wakeups. The Stop entry blocks turns that end in a prose question, directing the model to re-ask through AskUserQuestion. State records the exact entries setup added; foreign entries (including identical pre-existing ones) remain unowned. Status lists owned hooks as applied or missing; install re-adds a missing or edited owned entry and leaves the edited copy as yours, a duplicated owned entry causes a conflict, and uninstall removes only owned entries while preserving other settings and their key order.

When `~/.codex` also exists, setup writes the policy to `~/.codex/hooks.json` (Codex 0.141 or newer, where hooks are on by default): PreToolUse groups for `Agent|spawn_agent`, `Bash`, `mcp__t3_code__delegate_task`, `mcp__t3_code__t3_thread_send`, `mcp__t3_code__t3_thread_launch`, `mcp__t3_code__schedule_task`, `mcp__t3_code__create_threads` and `mcp__t3_code__watch_pull_request`, plus a `Stop` group, each running `policy-hook --host codex`. Claude's `.*` PreToolUse matcher sees these calls too. New T3 schedules are denied; a pause-only update to an identified schedule is allowed, while list/read, deletion and cleanup remain available. Worker-tagged events cannot create threads, watches, or local wakeups. Codex does not expose reliable standalone Manager/Worker role metadata, so top-level thread creation, new PR watches, and recognized shell-based automation creation fail closed; existing watches are unaffected. Ordinary delegation and unrelated shell work remain available. Automation registration and lifecycle rules are documented for Manager and Infra review, not inferred from tool text. Codex cannot prompt from a hook, so every approval the Claude hook would ask for becomes a deny that tells the model to get the user's approval and retry. Codex runs a user hook only after it is trusted. Install writes the hook entries without trusting them. Run `agent-workbench trust` to review and consent to adding owned `[hooks.state."<key>"]` tables with `trusted_hash` to `~/.codex/config.toml`; without a terminal, or when you decline, it prints the `/hooks` step to trust them in Codex. A foreign `hooks.state` entry for the same key is left alone and reported. Status adds `codex_hooks` (applied or missing) and `codex_trust` (trusted, untrusted, or modified), with JSON output available through `status --json`. Uninstall removes only the owned tables that are still unmodified. Editing an owned hook's command or timeout, or moving it in `hooks.json`, changes its hash or key, so it becomes untrusted until install runs again.

`agent-workbench uninstall` removes both managed instruction blocks and owned import/launcher, and makes Codex's file regular again with the current private text. Backups remain private under `~/.local/state/agent-workbench/backups`; uninstall never restores stale snapshots over later edits. This is the normal rollback operation. Review retained backups manually for historical recovery.

If a command reports an override, foreign entry, missing resource, or edited managed block, preserve the files and resolve that specific conflict before retrying. There is no force-overwrite mode. State and lock live under `~/.local/state/agent-workbench/`.

When the Claude Code config directory exists, installation manages `autoCompactWindow` from `max_tokens`, `modelSettings.<model>.autoCompactWindow` for each `manager_models` entry when `manager_window` is set (null by default), and optional `env.CLAUDE_CODE_MAX_CONTEXT_TOKENS` from `gateway_window`. Per-model compaction requires Claude Code v2.1.288 or later. `policy.context.worker_window` is null by default; when set to at least `100000`, it adds `autoCompactWindow` to every generated Claude subagent. Claude Code applies this frontmatter only to subagents and caps it at the window granted by that model's settings, so it only lowers the window. It does not affect `codex exec` Workers. Generated subagents also set `disallowedTools: AskUserQuestion`. Install removes the previous owned `env.CLAUDE_CODE_AUTO_COMPACT_WINDOW` when its value still matches state. A user-set copy takes precedence over both window settings. Install and status warn when a Worker tier shares a Manager model and its window.

When the Codex config directory exists, installation manages `model_auto_compact_token_limit` and optional `model_context_window`. When `manager_window` is set, pass `-c model_auto_compact_token_limit=<manager_window>` in the launch arguments for a Codex Manager only, for example in T3 Code's Codex provider launch arguments. `codex exec` Workers use the shared limit.

Setup preserves other settings, including provider routing and existing compaction windows that already match. A differing foreign value or an edited owned value conflicts. Missing managed values are reapplied. Status reports each key and uninstall removes only unmodified owned values. Restart running sessions to pick up changes. At the cap the harness compacts in place in the same thread and the Manager takes no action. Compaction does not enforce a hard request-token limit. Installation does not edit other skills, project files, shell configuration, credentials, or permissions.

For isolated fixtures, put the skill at the canonical location under a disposable home, then pass `--home PATH` before the command. Alternate-home updates require an explicit `--skills-cmd` executable command; they never default to the real user's npx update. Native permission choices remain with the user.
