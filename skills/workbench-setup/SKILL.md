---
name: workbench-setup
description: Install, inspect, update, or remove Agent Workbench shared global instructions and its local launcher while preserving personal instruction text.
---

Use the bundled Node.js 22.20+ installer on Linux or macOS. Native `npx skills` distributes this skill; it does not execute the installer or apply global prompts.

`workbench.mjs help <command>` and `<command> --help` show command usage. `status` prints a readable checklist; use `status --json` for the same machine-readable status fields.

Orchestration's interactive Manager, native Worker ladder and configured context policy live in the `orchestrate-harnesses` skill. Window values come from base `policy.context` in the Worker configuration, not skill or role instructions. Updating that skill changes its distributed defaults, not the current Manager's interactive model/settings or the user's partial model overrides.

After global distribution, explicitly apply the setup:

```sh
node ~/.agents/skills/workbench-setup/scripts/workbench.mjs install
awb status  # alias for the installed agent-workbench command
awb trust  # optional: consent to trust installed Codex hooks
# Or use ~/.local/bin/agent-workbench status and trust
```

The installer creates `~/.agents/AGENTS.md`, links Codex's `~/.codex/AGENTS.md`, and ensures `~/.claude/CLAUDE.md` has one native import resolving to the shared instructions. An existing equivalent Claude import is reused. Personal text belongs outside `<!-- BEGIN agent-workbench -->` / `<!-- END agent-workbench -->` and the optional `<!-- BEGIN agent-workbench personal -->` / `<!-- END agent-workbench personal -->` block in the shared file. When `~/.agents/skills/workbench-personal/AGENTS.md` exists, install applies it in that second block immediately after the public block; removing the package or file removes the owned personal block on install. Both blocks have ownership and drift checks; edit the package source instead of the installed personal block. Existing Codex regular-file bytes are kept outside the managed block on first installation; existing Claude text stays in its file.

`agent-workbench install` reapplies distributed assets. On Linux with a supported sensor and user systemd, opt in to the thermal logger with `awb ops thermal install` or `agent-workbench ops thermal install`. Use the corresponding `ops thermal uninstall` command before removing the skill if you enabled the logger. `agent-workbench update` first updates installed skills owned by `onsager-ai/agent-workbench` plus `workbench-personal` from any source through the native skills lock, then runs freshly distributed setup code. Node.js 22.20+ is the only runtime needed (`npx` distributes and updates the skills). Do not edit the native skills lock yourself.

When `orchestrate-harnesses` is installed, `install` (and `update`) generates one Claude Code subagent per routable tier at `~/.claude/agents/<tier>.md`. Distributed `workers.yml`, optional `~/.agents/skills/workbench-personal/workers.yml`, the partial user override (in that precedence order), and every profile contribute to this union. A tier is routable when it has `harness: claude` (using `model`) or a non-null `claude_route`. The default ladder maps L1, L2 and L3 to haiku, sonnet and opus. The optional `codex` profile maps luna and haiku to L1, sol and sonnet to L2, and adds opt-in terra with null routes, so Claude Managers run Codex Workers as `codex exec` unless a user override supplies a gateway model ID. Users can map any models to levels in `workers.yml`. Change a route in the YAML override, or set it to null to remove it when no profile needs it. A tier name must use the same model, route and effort across profiles; rename conflicting tiers. Each agent carries model and effort in frontmatter and the Worker instructions as its prompt. Rerun `agent-workbench install` after edits. Without `orchestrate-harnesses` no agents are generated.

Use `agent-workbench workers --cwd PATH` to print effective JSON and the selected profile. Overrides live at `$XDG_CONFIG_HOME/agent-workbench/workers.yml` when XDG is nonempty and absolute, otherwise `~/.config/agent-workbench/workers.yml`. The `yaml` and `smol-toml` packages are vendored; installation never runs `npm install`. Setup owns a resolved `workers.json` beside `state.json` and passes its path to the policy hook. The hook selects approval rules by dispatch cwd; missing or unreadable policy asks for approval and requests reinstall. Uninstall removes the unmodified owned JSON along with the agents and hook entries.

Generated agent files are recorded with content hashes in the state file. Setup never overwrites a file it does not own, or an owned file you edited, and reports a conflict instead; other files in `~/.claude/agents` are left alone. `status` lists owned agents, personal package presence and applied personal files; `uninstall` removes unmodified owned agents.

When `orchestrate-harnesses` is installed, setup adds four Claude Code `hooks.PreToolUse` entries, one `hooks.PostToolUse` entry matching `Agent|Task`, and one `hooks.Stop` entry in `~/.claude/settings.json`, all running the installed `orchestrate-harnesses/scripts/policy-hook`. The PreToolUse entries match `Agent|Task`, `Bash`, and `mcp__t3-code__delegate_task` to require approval for L3 Workers (Opus by default), deny GitHub polling commands, and require explicit Worker models for built-in agents and T3 delegation. PostToolUse checks the resolved route at async launch and checks the route and transcript models on completed runs. It reports the observed model if the configured model is an alias and the hook lacks its effective target. The Stop entry blocks turns that end in a prose question, directing the model to re-ask through AskUserQuestion. State records the exact entries setup added; foreign entries (including identical pre-existing ones) remain unowned. Status lists owned hooks as applied or missing; install re-adds a missing or edited owned entry and leaves the edited copy as yours, a duplicated owned entry causes a conflict, and uninstall removes only owned entries while preserving other settings and their key order.

When `~/.codex` also exists, setup writes the same policy to `~/.codex/hooks.json` (Codex 0.141 or newer, where hooks are on by default): PreToolUse groups for `Agent|spawn_agent`, `Bash`, `mcp__t3_code__delegate_task` and `mcp__t3_code__t3_thread_send`, plus a `Stop` group, each running `policy-hook --host codex`. Ownership follows the Claude rules above. Codex cannot prompt from a hook, so every approval the Claude hook would ask for (L3 or approval-required tiers) becomes a deny that tells the model to get your approval and retry, and the rule against inheriting the Manager's model does not apply. Codex runs a user hook only after it is trusted. Install writes the hook entries without trusting them. Run `agent-workbench trust` to review and consent to adding owned `[hooks.state."<key>"]` tables with `trusted_hash` to `~/.codex/config.toml`; without a terminal, or when you decline, it prints the `/hooks` step to trust them in Codex. A foreign `hooks.state` entry for the same key is left alone and reported. Status adds `codex_hooks` (applied or missing) and `codex_trust` (trusted, untrusted, or modified), with JSON output available through `status --json`. Uninstall removes only the owned tables that are still unmodified. Editing an owned hook's command or timeout, or moving it in `hooks.json`, changes its hash or key, so it becomes untrusted until install runs again.

`agent-workbench uninstall` removes both managed instruction blocks and owned import/launcher, and makes Codex's file regular again with the current private text. Backups remain private under `~/.local/state/agent-workbench/backups`; uninstall never restores stale snapshots over later edits. This is the normal rollback operation. Review retained backups manually for historical recovery.

If a command reports an override, foreign entry, missing resource, or edited managed block, preserve the files and resolve that specific conflict before retrying. There is no force-overwrite mode. State and lock live under `~/.local/state/agent-workbench/`. Installation also owns `env.CLAUDE_CODE_AUTO_COMPACT_WINDOW` and optionally `env.CLAUDE_CODE_MAX_CONTEXT_TOKENS` in `~/.claude/settings.json` (replacing the earlier, unmodified `env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`) and `model_auto_compact_token_limit` and optionally `model_context_window` in `~/.codex/config.toml`, when the respective config directory exists. It preserves other settings, including provider routing. Foreign or edited owned values conflict; missing values are reapplied. Status reports each key and uninstall removes only unmodified owned values. Compaction is advisory, not a hard request-token cap; restart running sessions to pick up changes. Installation does not edit other skills, project files, shell configuration, credentials, or permissions.

For isolated fixtures, put the skill at the canonical location under a disposable home, then pass `--home PATH` before the command. Alternate-home updates require an explicit `--skills-cmd` executable command; they never default to the real user's npx update. Native permission choices remain with the user.
