# Automation policy

Before enabling recurring, unattended, or externally triggered work, a Manager records it in the personal registry at `~/.agents/skills/workbench-personal/automations.yml`, using [automations.schema.json](automations.schema.json). Claude Code requires a successful `Write` or `Edit` of that registry in the same turn before activation. Workers do not create or enable automations. Bind each entry to a host, project, configured model, schedule, cost cap, and end condition. L1/L2 are the default; Opus requires an owner L3 approval line. Money, public actions, and credential use each need their own approval.

This policy covers T3 schedules, `/loop` and wakeups, system cron/systemd jobs, PR watches, daemons, and unattended threads. Use the current thread for a Manager's follow-up. Create a new top-level thread only on the owner's explicit request. When a dedicated scheduled thread completes its assigned work, it reports the result and settles itself; it never settles an ongoing Manager thread after a wakeup.

The hook enforces only what events expose. It denies new T3 schedules because that schema cannot select a model; a call that only pauses an identified existing schedule is allowed, and list/read, delete and cleanup calls are left alone. Claude checks a successful same-turn registry write for observable `/loop` Skill calls, PR watches, and cron/systemd/daemon command text. It validates the registry host against the current host, project against the tool's project or current directory, and model against the configured ladder. The registry's `cost_cap` and `end` are required records, but the hook cannot measure spend or guarantee a timer's end. `CronCreate` and PR watches do not accept a model field, so the hook cannot pin or verify their runtime model. Codex has no reliable standalone Manager/Worker role signal here, so top-level thread creation and automation activation fail closed; ordinary delegation remains available. Hooks cannot establish owner intent from natural language or inspect arbitrary scripts, services, or daemons. Thread settlement and unobservable wakeup behavior remain instructions. Existing schedules are not changed.
